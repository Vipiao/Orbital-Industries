# Design

The recipe in `03_source_recipe.md`, as changed to fit this engine and game. Where this file
and the recipe disagree, this file wins.

## The split

### Engine: scatter handler

A sibling of `CdlodHandler`. It knows it draws many items grouped in patches, and nothing
else. No name, comment or piece of logic in it mentions trees, ground, up, a planet or a cube
face.

Vocabulary:

- **kind** — one sort of item: its meshes per LOD, LOD distances, maximum distance, bounding
  radius, and optionally an impostor.
- **patch** — a caller-chosen region holding a fixed number of candidates. Has an origin in
  the body's frame (double), a bounding sphere, and an opaque payload only the snippet reads.
- **candidate** — one possible item in a patch, identified by its index. The index is the
  item's stable identity; its slot in the buffer is not.
- **item** — a candidate that was kept: position relative to the patch origin, orientation,
  scale, kind, candidate id.

What the caller does:

- At load: registers kinds (meshes, textures). The engine packs the meshes and bakes impostors.
- Creates a scatter program from an injected GLSL snippet, with named textures and uniforms,
  as a CDLOD surface is created. The snippet answers one question: given a patch's payload and
  a candidate index, is it kept, and if so where, how oriented, how big, and which kind.
- Creates an instance on an **SSBO index it passes in**, so the items ride the same transform
  as whatever else cites that index.
- Adds and removes patches. A patch is either generated by the snippet or filled from records
  the caller supplies.
- Suppresses and restores items by candidate id.

What the engine owns: buffers and slot allocation, budgeted generation, culling, LOD choice,
the visible lists, the indirect draws for the G-buffer and depth passes, the impostor bake,
the distance fade, shader reload.

### Game: planet vegetation layer

- Which patches exist: the equal-angle cube-face grid, and which of them are in range, nearest
  first.
- The snippet: hashes, jitter, slope/height/biome rules. Prefixed with the planet GLSL already
  generated by `planetSurfaceGlsl`, so items stand on the same full-detail surface the terrain
  draws.
- The kinds: trees, bushes.
- Later: the CPU twin for near patches, trunk capsules, destroyed ids per patch and their
  network sync.

## Changes from the recipe

### Frame of reference

The recipe assumes a static world. Here a body moves and rotates. Patch origins are in the
body's frame; the camera is placed in that frame in double on the CPU each frame; the per-patch
offset is uploaded as float; the body's rotation is applied to the camera-relative offset.
This is what `cdlod_patch.glsl` does, and the pose must be the same one CDLOD selected against.

### CPU/GPU agreement (deferred)

The recipe's bit-exact placement cannot hold here: terrain height is filtered texture lookups
plus `sin` and `sqrt`, float on the GPU and double on the CPU. Planned replacement, not in the
first iteration: one authority per patch — far patches generated on the GPU, near patches
computed on the CPU and uploaded as records, so collision and drawing agree by construction.
The first iteration generates on the GPU only; `addPatch` takes no items until G4 brings the
records path back.

Known cost when that arrives: a borderline candidate can appear or vanish when a patch changes
source. In multiplayer the server should own the verdict.

### Deferred shading

Items are drawn into the G-buffer. Impostors therefore need a normal layer from the start, not
as a later improvement.

### Shadows

Caster tiers as in CDLOD (`FrameRenderParams::casterTier`, `ShadowRenderer`'s cylinders). The
CPU sorts the patch list by tier before upload, exactly as CDLOD does.

The one difference: CDLOD draws its patches directly, so a prefix of the patches is a prefix
of the draw. Here patches are not drawn; their items pass through the culling pass into
per-(kind, LOD) lists, which loses the patch order. So for cascade *c* the culling pass is run
again over the prefix of the sorted patch list (without the camera frustum test), and its
result drawn. The visible list itself is never sorted. Near cascades cover few patches, so the
extra passes are small.

If measurement says those passes cost too much: one culling pass writing ranges grouped by
tier, so a cascade draws a prefix of the commands instead.

### Impostors

An impostor is one more LOD mesh of its kind: a quad in the same packed buffers, drawn by the
same commands. A per-LOD flag marks it camera-facing and the vertex shader turns it about the
item's own axis. A kind without one simply ends at its last mesh.

### Range limit

Hard cutoff at the kind's maximum distance for now. Fading (shrink or dithered discard) and
matching the terrain colour beyond it come later.

No hierarchical patches in the first version.

### Record size

Start with a plain, readable record. Shrink it (patch-relative position, packed orientation,
scale, kind, id; target 16–32 bytes) as its own step once the pipeline works and is measured.

## Risks

- **Near meshes, not impostors, are the cost.** The recipe measured 53k full meshes at 32 ms.
  Mesh LOD rings must be tight.
- **The 3 ms budget.** Estimated reachable at roughly 4–5 km radius at the recipe's density on
  an RTX 4070, from the recipe's numbers scaled; not measured here. Those numbers are probably
  forward-rendered without shadows.
- **Memory** grows with the square of the radius; fixed blocks per patch are paid for whether
  used or not.
- The engine has no compute shaders or indirect draws yet. `ShaderProgram` has no compute
  stage; adding one is step E2.1.
